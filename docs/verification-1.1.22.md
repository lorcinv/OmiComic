# OmiComic Android 1.1.22 工作报告

日期：2026-10-16。本轮只修正后台返回时的画面交接和开屏过渡。

> **同日补充复核：1.1.22 仍存在长时间后台、锁屏后的恢复闪烁。** 新测试已在同一安装包上复现，下面原有的短间隔检查不能作为此问题已解决的证明；本次补查没有修改正式代码或重新打包。

## 后续复核：长时间后台和锁屏

用户补充环境为一加 Ace 2、ColorOS 16；触发条件为后台数分钟或锁屏一段时间，短时间切换正常。本次对原 1.1.22 APK 增加长时间恢复检查，测试环境仍为 Android 15 / WebView 124 模拟器。

- 首页单独停留、从未打开资源库时，后台 3 分钟返回也出现内容短暂消失。因此不能把这次现象归因于首页与资源库互相切换。
- 资源库后台 3 分钟、锁屏 2.5 分钟及后台内存回收检查中，Activity、网页实例、原资源库元素均保持不变，未调用网页转场，未重新加载页面。
- 最终屏幕录屏确认首页、资源库和锁屏恢复存在只剩背景的间隔。同期应用窗口 PixelCopy 采样却仍是原内容、亮度波动为 0，说明此前只查应用窗口的验证方式无法覆盖最终屏幕的交接问题。单纯“纯色空白”判定也会遗漏有轻微渐变或残影的空画面。

确定的故障范围是恢复时的画面交接，而非页面重新加载。Chromium 的实现会在窗口持续不可见后释放绘图资源，之后在绘制时重建；页面实例可以继续保留。这一机制与复现规律吻合，但尚未直接取得用户手机上的底层绘制日志。[Chromium 实现](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/android_webview/java/src/org/chromium/android_webview/AwContents.java)

另外复现了两种独立的网页转场竞态：首次资源库尚未加载完、或后续转场仍在排队时进入后台，待操作在返回后完成，会继续播放动画。它们要求有未完成的切页请求，不能解释用户描述的稳定页面久置场景。

后续修复应覆盖“系统旧画面退场到应用实际首帧显示”的间隔，不能只依赖网页已准备绘制的回调。可采用一张有尺寸上限的临时末帧遮盖恢复过程，等实际绘制完成再移除；这是待实施方案，不是本次已完成的修改。

## 修改内容

**后台返回：保留已有画面，等网页首帧可绘制后再交接。** 原先在 onPause 就暂停网页，此时桌面可能还在使用应用窗口做切换动画；返回时也未阻止未准备好的首帧绘制。本版把网页暂停移至窗口完全不可见的 onStop，返回时增加首帧等待。恢复不会重新加载页面或播放启动动画。旧回调、快速再次切出及等待超时均有收尾处理。

**开屏：接续系统原有画面，再从中央展开首页。** 旧版先移除系统启动画面，再从空的圆形区域开始绘制首页，录屏中确实出现纯色间隔。本版先等首页与系统启动画面完成绘制，短暂保留系统实际显示的那一帧，然后用原生渲染线程完成约 420 毫秒的中央展开。没有重新设计或添加内部启动图标，也不再用 Java 逐帧裁剪网页。

Android 12+ 使用系统 SplashScreen 的实际画面；较早系统直接衔接准备好的首页。关闭系统动画时直接显示首页。冷启动底图最多 8 MiB，结束或中断过渡便移除并解除引用；不写入磁盘，不累加。后台返回不新增截图缓存，漫画的预读和缓存预算不变。

Android 的视觉状态回调保证下一次绘制可以反映指定状态，并不表示该帧已经显示，因此启动还需要等待实际帧提交；后台首帧则在回调前阻止空画面提前提交。[Android 官方说明](https://developer.android.com/reference/android/webkit/WebView.VisualStateCallback)

## ComicScreen 对照

检查了用户提供的 ComicScreen 2260 APK，SHA-256 为 `a565e7469804864e342a52188327994237c04952e548fb55d80038ed6cfa5baa`。

其主入口直接进入原生列表页面；列表与阅读页面返回时恢复必要状态，没有重建整个主界面，也没有在普通恢复流程里重播开屏。应用代码中未发现自定义 SplashScreen 退出动画。Omi 借鉴的是“保留页面、恢复必要状态”的处理方式，并针对网页绘制增加首帧等待。

这部分为 APK 结构、资源和代码检查。该包只有 arm64，现有模拟器为 x86_64 且没有 ARM 转译，因此未声称完成两款软件的同机运行对比。[检查记录](../test-results/mobile1122-comicscreen-audit.json)
