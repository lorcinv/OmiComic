# 1.1.49 全景撕裂复查与本地测试

状态：仅本地测试，未提交或发布到 GitHub。保留 1.1.49 版本号。

用户复测指出，PC 全景拖动画面仍有横向撕裂，静止后稳定；Android 也有轻微闪烁。上一轮的位置与小区域空白检查没有覆盖整幅图内部错层，不能据此认定撕裂已经修复。

## PC

此机器为 RTX 4070、2560 × 1440、180 Hz。保持同一安装程序和漫画，仅使用 `--disable-direct-composition` 切换 Windows 窗口呈现路径后，用户反馈撕裂消失，随后补充仍有轻微移动模糊。

本地测试版已将该开关内置于 Windows 启动流程。GPU 合成与栅格化保持启用；原有解码流程、图片质量、缓存、预加载、并发及 Android 渲染路径均不因该开关改变。Chromium 对此路径的实现见 [DirectComposition support](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/ui/gl/direct_composition_support.cc)。该对照定位到本机的窗口合成兼容问题，不能据此断言某个显卡型号或驱动版本必然存在该问题。

使用独立资料目录、自制 40 页 1062 × 1500 网格图，在最大化窗口比较发行版与内置修复后的打包程序。每组横向、纵向各拖动约 2.8 秒，实际图片均移动 477 px；测试前等待可见窗口加载与解码完成。两组都采集了 GPU 合成和交换事件，不仅统计脚本回调。

这组样本没有发现性能退步。主线程累计耗时变化约 -1.1% / +0.6%，不能解释为普遍提速或性能损失。内置修复的窗口未额外传入呈现开关，运行时仍确认 DirectComposition 关闭、GPU 合成与栅格化开启。

移动图像的横向逐行与纵向逐列检查没有出现错层。网格边缘仍保留原有缩放插值的对比度；没有新增运动模糊滤镜或降低图片分辨率。用户所说剩余的动态拖影不能仅凭截图确定来自显示器响应还是视觉暂留，最终以实际拖动体验为准。

## Android

原来分别对图片的四条边取整，固定尺寸图片在移动时会交替增减一个物理像素，造成整张图不断重新缩放。改为对起点与宽高分别取整，再计算终点，保持移动时的实际像素尺寸稳定；裁剪区域仍按边界取整。

同样处理原生预览图。继续沿用原生 Canvas、解码、缓存与帧合并，不新增绘图循环。1 / 1.25 / 2.75 / 3 倍像素密度的横竖移动尺寸检查，以及 Android 相关检查共 18 项通过；类型检查和原签名 APK 构建通过。实体手机体验待用户验收，不以桌面结果代替。
