# OmiComic 2026-10-29 修改优化清单

状态：1.1.42 源码修复与双端构建已实施，PC 安装验收记录见[修复与验收报告](2026-10-28-repair-1.1.42.md)。Android 15 模拟器七组原生运行测试已通过，具体范围和数据见[Android 验收报告](2026-10-28-android-1.1.42-acceptance.md)。实体手机、原生平板和十万条 Android 内存压力测试仍待验；下文保留原始需求与验收条件。

## 已确认的原则

- 保留当前资源库全部子目录的随机范围。资源清单持久化，“重随机”只重新排列已发现的漫画资源。
- 资源清单循序渐进建立：已有内容先显示，可见内容优先，缺少的内容在后台逐步补齐。禁止等全库扫描结束后才显示页面。
- 沿用当前可见封面优先、逐张返回、有限并发、附近预取及列表虚拟化设计。后台索引必须服从这些优先级。
- 修复以原版 1.1.40 的正常浏览和阅读体验为基准。现有嵌套压缩包修复继续保留。
- 共用功能规则，分别维护 PC 与 Android 的文件访问、缓存、并发和阅读优化；一端验收通过不能代替另一端。

重点保护的能力：

- **Android**：可见封面优先、并发 2、逐张发布、仍可见任务复用、取消无人订阅的任务；有界目录/URI 缓存、异步批量 SQLite 保存；文件夹封面可续建片段；ZIP pread、原生阅读显示、设备内存预算、前台/预取分离和上一完整帧保留。
- **PC**：目录 stat 共享上限与及时取消；桌面封面原有并发和缓存复用；ZIP 条目索引定位；归档前台优先和保留阅读通道、7z 有限并发；原分辨率阅读及字节预算预取。不能简单把手机的低并发搬过来。
- **共用**：虚拟列表、滚动锚点、稳定资源身份、重复请求合并、查询/导航代次、原文件读取校验与授权。保护调用行为和预算，不能仅以文件哈希没变作为性能无回退证明。
- **新功能接入**：普通目录先发布，再投递摘要；基础资源清单渐进持久化，搜索和随机读取摘要；一次发现供多消费者复用，局部变化局部更新；应用后台暂停，前台需求到来让出；已完成封面不因批次通知重做。
- **保持用户需求**：长路径、嵌套压缩包、平板自适应、返回位置、书签准确跳页及每页 500 保留。对无调用旧支路清理前核对引用；不要把未执行的代码列成实际性能损失。

本轮函数诊断的重要结论：相同 1 万条示例数据，手机旧/新匹配函数在开发机上均约 50 ms，主要新增成本来自范围扩大和新调用链；PC 空查询从约 0.19 ms 增到 44.51 ms。现有随机函数从 10 万个短 ID 抽 50 个约 4.59 ms，不能把数秒等待归咎于无偏随机算法。以上均非实体手机速度；完整结果保存在审计报告引用的 measurements.json。

这些条目贯穿后面的需求实施，不另造一套与现有目录/封面/阅读器并行竞争的加载器。

## 零、优先修复手机版搜索性能回退

用户新增反馈：最新手机版搜索明显变慢，旧版没有同样体感。对照原版 1.1.40 与当前代码，已确认新增的性能慢路径和一处缓存复用错误；具体设备耗时待实际复测。

代码依据：

- 原版 LibraryPage 搜索过滤当前已加载目录；当前穿透搜索改为获取全库清单，Android scanLibrary 遍历全部目录后才一次返回。扩大搜索范围增加了工作量，但不应把全部工作作为首批结果的前置等待。
- LocalLibrary.children 与 scanLibrary 的目录版本键拼接不一致：前者使用实际换行符，后者使用字面量反斜杠+n。即便目录 URI、时间、大小和代次相同，持久缓存键也不相等，扫描因此无法复用该磁盘缓存；短时内存缓存仍可能命中。
- cancelLibraryCatalog 在取消搜索时清除完整搜索清单缓存；重新搜索可能再次扫描。现有清单有效期只有两分钟，到期也会重新走全量准备。
- 清单加载后，搜索词变化会在界面线程同步过滤大列表；逐资源解析查询和规范化文本的成本在原版手机已存在，本轮被扩大为全库，并增加父分支映射和排序。大库连续输入存在阻塞输入和绘制的风险。PC 另有丢失空查询快速返回的问题，按 R04 单独修。

修改任务：

- [ ] 将目录版本键生成集中为同一个函数，修正读写两端不一致，并验证持久缓存真实命中，而不只检查返回结果正确。
- [ ] 取消搜索只停止该搜索会话的待处理任务，不销毁仍有效的基础资源清单，不误取消其他消费者的任务。
- [ ] 使用后文的渐进共享清单：已知资源先搜先显示，未知部分分批补充；补充期间输入、清空、返回和导航保持响应。
- [ ] 查询表达式每次变化只解析一次；资源的规范化搜索字段按版本复用，元数据变动时局部更新，避免每个字符都重新处理所有文本。
- [ ] 大范围匹配采用可中止的后台或分片任务，结果携带查询代次；输入框立即更新，旧查询结果不能覆盖新查询。中文输入法组合输入与确认分别处理，不能边组词边堆积全库任务。
- [ ] 已有结果在后台校验时继续可用；缓存到期只安排增量检查，不将页面清空后重新等全库完成。
- [ ] 使用新的文件夹名称匹配和文件穿透结果规则，移除额外的祖先映射构建。

验收单独记录：首次搜索出首批结果的时间、同库重复搜索、逐字输入/删除的响应、清空后重搜、重启后的磁盘缓存复用，以及后台补清单时的返回与切页。覆盖已完整缓存、部分缓存、缓存到期和目录无可靠修改时间的情况；记录源目录枚举次数、缓存命中和界面长任务，不能只记录“最终能搜到”。

## 五、随机改成共享排序，资源清单渐进建立

### 5.1 撤掉当前随机专用的重活

- [ ] 删除候选缺失时“点击随机 → 递归枚举整个资源库 → 等全部返回 → 生成候选”的前置等待链；已有候选的内存重抽路径按共享排序重构。
- [ ] 删除收藏、书签在开启随机时逐条执行 checkResourcePath 的全量预检查。
- [ ] 移除随机自己的独立候选副本、扫描生命周期和与搜索共用的全局取消副作用。
- [ ] 复用原排序、过滤、分页、虚拟列表和可见封面加载流程，随机只成为一种有效排序方式。
- [ ] 保留现有随机阅读入口位置。开关与排序显示使用同一状态：开启后显示随机排序；选普通排序即退出；关闭开关恢复此前的普通排序和浏览位置。

现状依据：useRandomBrowse 仍依赖 loadLibraryCatalog；PC 和 Android 的 catalog 接口都在遍历完成后才一次性返回整个列表。排序算法本身已经在内存执行，主要额外成本来自获取候选、路径检查、数据复制和与正常加载争抢磁盘。

### 5.2 “先显示，再补全”的建立顺序

1. 打开页面先走现有目录读取与已有列表显示，不等待全库清单初始化。
2. 复用已持久化的资源摘要、当前目录读取结果和已有目录缓存。相同目录的同一次读取结果直接供清单使用，不能再读一遍。
3. 可见卡片逐张加载封面，沿用现有队列；不以一组封面全部完成作为显示条件。
4. 只有当前页面没有高优先级需求时，才分批枚举尚未访问的目录。接近屏幕的封面仍先于远处目录索引。
5. 滚动、切目录、打开漫画、阅读翻页时，暂停派发后台索引工作；在安全边界让出已执行的任务，操作结束后从断点继续。
6. 每批目录完成就提交记录和进度，不等待所有目录完成。界面更新合并限频，持久化批量写入，避免每条文件触发重绘或一次数据库事务。
7. 应用进入后台时暂停主动扫描并保存检查点；下次恢复继续，不重新从根目录扫描。

优先级：当前阅读与目录导航 > 当前可见封面 > 附近有限预取 > 后台资源发现与持久化维护。独立线程不能消除磁盘竞争，必须同时控制任务派发和 I/O 预算。具体批量大小、并发和时间片以 PC、手机测量确定，不预先写死一个全设备通用的激进数值。

### 5.3 持久化结构及占用约束

- [ ] 保存资源标识、父目录、相对路径、类型、必要的变化信息和扫描完整性；不把封面、图片内容或压缩包页数据塞进这份清单。
- [ ] 目录清单、漫画候选和搜索视图使用同一份基础记录；元数据按需取用，不在几个组件中复制完整对象数组。
- [ ] 手机复用现有 SQLite 目录索引设施，增加完整资源摘要和建表检查点。现有 DirectoryIndex 的 128 个目录快照、32000 条 URI 缓存及短有效期只是访问缓存，不能直接冒充完整资源清单，也不能粗暴放大这些缓存上限。
- [ ] PC 优先采用按资源库、按目录分块的轻量持久化，局部更新和原子提交；避免一个巨型 JSON 每次全读全写。最终存储格式在原型测量后确定。
- [ ] 启动时只读取当前视图需要的摘要；随机排序使用紧凑的资源编号，再读取当前页的元数据，不把全库所有路径与封面对象一次性送入 WebView。
- [ ] 纯图片漫画目录只占一个随机候选；详细页清单继续在进入漫画时按需读取。
- [ ] 元数据持久化与封面缓存分账统计，记录磁盘大小、常驻内存、首次构建峰值和重复打开的读取量。

占用说明：持久化会增加磁盘数据和首次/增量更新成本；内存也不会为零。仅以 32 位资源编号计算，10 万条排序编号约 0.4 MB；完整路径、数据库索引及运行时对象的占用另计，不能拿编号大小当总内存。目标是少量元数据换掉重复扫盘，不能以拖慢启动和首屏为代价。

### 5.4 完整性、更新和错误恢复

- [ ] 新库没有完整清单时，先使用已发现的漫画显示可用结果，并轻量提示仍在补全。未发现的漫画不可能参与均匀随机，因此此时不能宣称已覆盖完整全库。
- [ ] 当前随机批次保持稳定；新发现的漫画先进入下一次“重随机”的候选，不自动打乱正在浏览的卡片。
- [ ] 索引完整后，重随机覆盖整个资源库；缓存过期只安排后台校验，不能清空列表强迫用户重新等待。
- [ ] 应用内新增、删除、移动、重命名操作同步更新相关记录；当前目录刷新只更新相关目录。手动全库重建作为明确操作，不绑定每次随机点击。
- [ ] 外部变化通过可用的目录通知或空闲分段检查补齐。Android 文件提供器未必提供可靠修改时间，不能仅凭根目录时间断言所有子目录都没变。
- [ ] 每个目录独立记录“完整读取/待检查/读取失败”。部分扫描或授权失败不能把未读到的资源当作全部删除。
- [ ] 失效路径在实际显示、打开或局部校验时处理，不在每次随机前全量核验。需要补位时从本次顺序的后续候选取用，限制尝试次数。
- [ ] 清单可重建，损坏时保留可用旧记录并逐步恢复；不影响收藏、书签、阅读进度或原文件。

### 5.5 随机排序和一页限制

- [ ] 从当前资源库的已知候选编号建立随机顺序，再显示前 N 个；N 使用当前每页数量。
- [ ] 使用系统随机源和无偏洗牌，不采用 sort(() => Math.random() - 0.5)。可以只计算足够确定前 N 位的洗牌部分，结果必须等价于完整均匀洗牌的前 N 项。
- [ ] 每批内部不重复；不同批次允许重复抽中，不能人为排除上一批导致概率偏移。
- [ ] “重随机”只生成新顺序和当前页，不发起目录扫描、全量路径检查、压缩包解包或全库封面加载。可见卡片的正常按需封面请求仍保留。
- [ ] 阅读返回保留原批次、顺序和位置；再次渲染、封面完成或后台补清单不能触发新一轮随机。
- [ ] 搜索与标签筛选先应用，再对命中的漫画资源随机；目录导航入口不占随机名额。退出随机恢复普通搜索的文件夹区和漫画区。
- [ ] 每页数量变化只调整当前随机顺序的可见前缀；减少再增加时尽量保持已有相对顺序，不无故重抽。
- [ ] 切换资源库或导航栏目结束旧随机会话；空库与资源少于 N 时正常显示，不死等凑满。

主要入口：src/hooks/useRandomBrowse.ts、src/library/randomBrowse.ts、src/library/libraryCatalog.ts、LibraryPage 排序管线、electron/services/libraryCatalog.ts，以及 Android 的 LocalLibrary、DirectoryIndex 与桥接接口。普通目录/封面/阅读器已有优化优先复用，调整接入点和后台任务协调，而不是另造一套加载器。
