## 问题、根因和修改

| 用户反馈 | 已确认原因 | 修改位置与行为 |
| --- | --- | --- |
| PC 大图预览感叹号 | 预览沿用旧 12 MiB／1600 万像素拒绝上限，和正文的大图路线不一致 | `electron/services/pagePreviewService.ts`、`electron/main.ts`：异步 `nativeImage.createThumbnailFromPath`；最长边 360，冷请求串行、同签名合并、160 项小图缓存，压缩包暂存文件完成后删除 |
| 右键缺少打开路径 | PC 菜单没有复用手机的目录定位入口 | `LibraryPage.tsx`：资源库、最近、收藏、书架内资源、书签共五处菜单；进入应用内资源所在目录 |
| 最近阅读卡片先跳位 | 打开前先写进度并刷新最近列表 | `LibraryPage.tsx` 只传递起始页；由已显示的 `ReaderPage` 保存进度，延后更新排序 |
| 放大后不能点击翻页 | pointerdown 即当作平移并清除点击起点 | `useReaderZoom.ts`、`ReaderPage.tsx`：鼠标移动超过 4 px 才消费拖动；静止点击保留翻页；触摸捏合逻辑保留 |
| 手机放大久糊 | 细节任务排在整页预读后，多个 PNG 小块重复扫描 | `NativeReaderSurface.java`：独立 details 队列；100 ms 缩放安静期后补可视区域；合并为单个有界区域，移除该区域额外逐像素滤波 |
| 双端加载倒退与闪烁 | 普通页仍做重核滤波；PC 小图被全局串行限制；拖动反复暴露原层；手机预览被正文阻塞 | 普通页短核低通；PC 小图恢复 4 路／后台最多 3 路，大图受预算限制；已呈现画面运动时保持，新页继续准备；手机预览独立请求／恢复 |

这次确实存在新旧优化衔接不一致。单纯判断“文件超过 5 MB 就完全解码原图”不能解决问题：压缩字节数不能代表像素内存。大图保留系统采样、原图显示或有界视口读取，避免强制所有图片 `sample=1`。

### 画质与速度的具体平衡

1. **正文尽快显示**：PC 原图解码后直接显示，不等待滤波；Android 大图使用系统采样底图，不扫描全图做 Java 自定义滤波。
2. **普通页保留轻量抗混叠**：PC GPU 使用截断高斯核，标准差约为目标像素的 0.75，支持范围约 2.25 个目标像素；无 WebGL 的软件降级仍保留原有有界质量路线。Android 不超过 100 万像素的普通 PNG 保留现有快路，大一点且完整临时像素不超过 `min(64 MiB,maxHeap/8)` 时使用原生 PNG 解析加同类短核低通，超预算保留原来的有界逐行解析；短核继续复用重复行缓存与灰度计算优化。微型 PNG 的原生完整解析加通用卷积实测反而比旧行缓存慢，因此没有一刀切换。
3. **运动中稳定**：已完成画面不因每次几何更新先隐藏；停止后再细化。新进入的页面继续准备，不能把“延后细化”扩大成“拖动时完全不处理新页”。
4. **放大补原始细节**：PC 从完整原图只重画当前视口；Android 对当前区域原生解码并用 Canvas 轻滤波，不再额外完整卷积。新旧区域合计受 tile 预算限制，每个新计划最多使用分配额一半，避免首次区域吃满预算后无法更新。
5. **可见预览独立**：手机预览条不等待正文邻页；恢复丢失的预览只解码不超过约 320 px 的小图，缓存预算 4 MiB。

已撤回两种尝试：PC 纯 Canvas 连续缩半在网点测试出现约 19 的亮度标准差；Android 纯缩半以及 Canvas 多次混合在斜纹测试出现最高 4～5 色阶误差。最终短核方案通过原有严格断言，没有为过测放宽画质标准。

### 本机滤波对比

与 1.1.57 的 Worker 对同一合成网点图对比，丢弃首次预热，交替运行，每组各 8 次：

| 原图 → 显示尺寸 | 原 Lanczos3 中位耗时 | 新短核中位耗时 | 降幅 |
| --- | ---: | ---: | ---: |
| 1062×1500 → 583×824 | 55.65 ms | 42.85 ms | 23.0% |
| 2400×3200 → 720×960 | 228.55 ms | 170.40 ms | 25.4% |

两组新方案网点亮度标准差约 0.50，均值约 127.5。证据为 `output/reader-1158/sampling-benchmark.json`、`benchmark.cjs`。这是本机 Headless Chromium 的 Worker 执行／传递诊断，**不是整本打开速度或手机真机提升百分比**。

## 文件与接手路线

优先看：

- `electron/services/pagePreviewService.ts`、`electron/main.ts`：预览路线与边界。
- `src/reader/desktopDecodeQueue.ts`、`src/hooks/useReaderDisplaySampling.ts`、`src/hooks/useReaderViewportRaster.ts`、`src/reader/displaySampling.worker.ts`：PC 预算、优先级、滤波和显示。
- `android/src/io/github/lorcinv/omicomic/ReaderBitmapDecoder.java`、`DisplayResampler.java`、`NativeReaderSurface.java`：手机解码分流、短核、视口区域与预览。
- `src/pages/LibraryPage.tsx`、`src/pages/ReaderPage.tsx`、`src/hooks/useReaderZoom.ts`：目录菜单、历史排序、点击／拖动。
- `tests/reader-regressions.spec.ts`、`tests/reader-halftone.spec.ts`、`tests/large-images.electron.cjs`、`tests/android/SmokeTest.java`：回归入口。

接手时沿这条路线继续：

1. 在共享工作区直接核对源码，不要再应用累计补丁；迁移到新目录可用本版完整源码 ZIP，或在匹配基线的干净工作区先 `git apply --check`。
2. 优先复测用户手机和本机安装后的真实漫画：快速翻页、远距跳页、放大拖动、预览条连续滑动，分开记录文件读入／解压、解码、滤波、细节补图时间。
3. 跟进用户 ZIP 第一次冷跳的约 5.8 秒等待；当前只能确认仍有加载等待，不能归为界面死锁。需要进一步分段记录，避免把压缩包总大小直接当作单页解码成本。
4. 手机若仍久糊，先看 details 队列、计划 sample、可视区域字节与可用 tile 预算；不要恢复整页逐像素卷积，也不要取消内存上限。
5. 只在问题复现后修改对应阶段，保留原有目录索引、缓存、前台保留通道、混合页序和页面身份。另一账户修改同一文件前先登记并核对差异。

## 构建命令

Windows：`npm run package:prepare` 后运行 `npx electron-builder --win nsis --x64 --publish never --config.directories.output=release/OmiComic-1.1.58-本地版`。

Android：`npm run build:android:renderer` 后运行 `scripts/build-android.ps1 -JavaHome <本地 JDK17> -OutputDirectory release/OmiComic-1.1.58-本地版`。签名沿用本机 `.android-signing`，不要将密钥／密码带入源码和交接包。

模拟器测试使用 `scripts/test-android.ps1 -Serial emulator-5680 -Mode large-images/quality1155/mobile-preview-speed -JavaHome <本地 JDK17>`，三个 Mode 分开运行。预览条在当前专用 AVD 使用 `-Fixture halftone-root`，需要中性 2500 页 `Many.cbz` 位于已授权的 Halftone1149 测试目录。不要将测试脚本用于用户手机。
