# OmiComic 原版 1.1.40 → 当前 1.1.41 性能审计

审计日期：2026-10-28。用途：补充 2026-10-29 修复清单。本轮没有修改应用代码、依赖、版本号或安装程序。

## 1. 基线、范围和判断方式

- 原版基线：`ae4ee1139fc92aec72a0183889d9c8bd7fee9dcb`，包版本 1.1.40，提交说明为原版首页、说明及 GPLv3 发布。使用此提交比较，不把此前误用 1.1.40 版本号的本地修改包当原版。
- 当前对象：工作区 1.1.41，包括未提交的新文件。检查 `src`、`electron`、`android/src` 及两个 package 文件，共 159 个文件：121 个内容未变、28 个修改、10 个新增；按统一换行后的内容比较。这是源码清单，不是 159 个功能测试。
- 方法：逐项比较差异，沿调用链检查筛选、扫描、传输、封面、阅读和导航；对实际搜索函数、随机函数、前端缓存模块和 PC 清单模块做独立诊断。
- 标记分为「代码已确认」「隔离复现」「待设备量化」。代码确认额外工作或错误，不等于已经测出每台设备的卡顿时长。本轮未启动打包程序或实体 Android 设备做新一轮端到端测量。
- 两端共用需求和数据规则，但不共用一套文件访问、并发、缓存预算或阅读渲染实现。下列每项单独标注平台。

总体判断：退化主要集中在新功能的接入层。原有封面队列、原生阅读、导航和预取模块大多还在，但新增调用绕过了部分复用规则，又把全库处理放进了首批显示之前。不能再用“核心文件没改”证明体验没有回退。

## 2. 基于代码差异的修复项

### R01 · P0 · 共用：首批结果被全库完成条件阻挡

**原版**：搜索筛选当前已经加载的目录列表。**当前**：`LibraryPage.tsx:1080` 切换到全库清单，`libraryCatalog.ts:19` 等原生接口完整返回，`LibraryPage.tsx:8777` 在 loading/error 分支替换掉列表。开启随机时先把会话设为空批次，再等候选全集准备完成。

PC 的 `electron/services/libraryCatalog.ts:21` 遍历全部目录后返回；Android 的 `LocalLibrary.java:239` 也在整个队列结束后返回一个 JSONArray。扩大搜索范围是需求，扩大首屏等待不是必需代价。

**修复**：正常目录继续即时显示；查询已知清单即可先出结果，未知部分增量到达。加载/局部错误只增加状态提示，不遮住已有结果；随机第一次可用已知候选，当前批次不被后续批次打乱。验收首批可用时间，不只看全量结束时间。

### R02 · P0 · 共用，后果分端：取消任务会删除有效清单，取消范围也过大

`src/library/libraryCatalog.ts:8` 的 `cancelLibraryCatalog` 清掉所有根目录的非 books 缓存和 pending；`useRandomBrowse.stop` 在关闭随机和范围变化时调用它，普通取消搜索也调用它。取消一个消费者不应清除其他资源库的数据。`useLibraryCatalog` 的 250 ms 是启用/根目录变化后的启动延迟，并不是每个输入字符的防抖。

**隔离复现**：同根目录连读两次只调用一次底层；准备两个根目录后取消，再读两个根目录，底层调用累计从 2 次升到 4 次。取消搜索会跨资源库丢掉前端复用结果。

- **Android**：没有对应的完整清单原生结果缓存，重复请求会重新遍历，只有部分前台目录缓存可能复用。
- **PC**：原生服务另有两分钟缓存；本轮复现确认取消后短时再次查询仍可命中，不能说 PC 每次取消都重扫磁盘。但仍有重复 IPC、结果筛除和对象传输；缓存过期后才重扫。

**修复**：按根目录、任务和消费者管理订阅、取消及代次；已完成元数据独立保存。两分钟到期转为空闲增量校验，不能清空清单。完整/仅漫画视图共享基础记录和进行中的发现任务，避免 Android 分别建两份清单。

### R03 · P0 · 共用：旧的逐项搜索成本被全库规模放大

原版手机版 `matchesMobileSearch` 已在每次调用中规范化文本并解析查询，这不是本轮新造的逻辑。当前把它用于全库，也引入 PC；`LibraryPage.tsx:1628` 还同步过滤列表，`searchHierarchy.ts:5` 每次重建全库路径 Map 并投影父分支，之后排序。长路径增大单条文本工作量，不能靠截断文件名处理。

**修复**：查询只编译一次；记录的规范化字段按版本复用；后台或可中止分片执行大批匹配，查询代次隔离，输入法组词期间不堆任务。移除用户已取消的祖先投影：文件夹只匹配自身名称，命中文件穿透列在后面。分页与虚拟化不能代替上游查询优化。

### R04 · P1 · PC 独有的新退化：空搜索失去快速返回

原版 PC `匹配桌面整理搜索` 在查询为空时立即返回 true。当前统一调用 `matchesMobileSearch`，在发现查询为空之前，已经对名称、全路径、备注和标签执行 NFKC/小写转换。因此普通打开目录、切换普通排序等触发筛选重算时也有额外成本。

**隔离复现**：1 万条、每条三个文本字段、空查询，原版 PC 规范化调用 0 次，当前 30000 次；本机函数中位耗时约 0.19 ms → 44.51 ms。原版手机版本来就做这些规范化，不能把此项说成手机版本轮新增。

**修复**：统一语法保留，恢复空查询快速路径；不要回退成两套语法。非空查询使用 R03 的预编译与字段缓存。测试普通浏览和切排序的无搜索情况。

### R05 · P0 · Android 独有：目录持久缓存版本键不一致

`LocalLibrary.children:182` 使用 Java 换行转义 `"\n"`；新 `scanLibrary:251` 使用字面反斜杠加 n `"\\n"`。相同 URI、时间、大小和 mediaEpoch 生成不同键，扫描器无法命中原目录磁盘快照。30 秒内存缓存仍可能命中，不能概括成所有缓存失效。PC 没有这段 Java/SQLite 调用链。

**修复**：共用版本键生成函数；验证正常读取写入后，扫描器确实读到同一快照。覆盖进程重启、时间为 0、目录真实变化、过期和授权撤销；不能只测返回结果正确。

### R06 · P0 · Android 独有：扫描发现的路径未接入快速 URI 定位

新扫描器自己查询 DocumentsProvider，既不保存发现条目的 URI 索引，也不提交目录快照。原 `children` 会把 URI/快照异步批量写入 DirectoryIndex。结果是搜索或随机已经读过的陌生深层路径，在后续封面、路径校验、打开阅读的 `resolve:123` 中，仍可能因无缓存而逐级枚举祖先目录。

不把全库塞进前台 64 个目录/32000 条缓存是正确意图，但完全断开数据复用产生了第二轮工作。

**修复**：后台发现结果分批写入共享持久摘要和可用的 URI 记录，活动目录继续使用有界热缓存。保存读取完整性，身份信息经过现有授权检查后才能使用；对实际选中项做局部新鲜度校验。验证“扫描发现 → 出封面/打开”不再逐级重复枚举，不能仅修 R05。

### R07 · P0 · Android 独有：全库扫描持有读锁过久

`LocalLibrary.call:622` 将整个 scanLibrary 包在公平 `fileAccess` 读锁中。它不直接排斥其他读者；但用户改名、移动、删除或清缓存需要写锁，写请求会等全库扫描，公平锁下后到的读取又可能排在写请求后面。原版锁保护的是单次目录/资源操作，本轮扩大成全库生命周期。

**修复**：按有界目录批次取得必要保护，查询、取消和提交边界明确；写操作更新代次并使受影响批次重新校验。不要简单去掉锁。实际慢文件提供器中测锁等待、扫描中改名及随后打开漫画的响应。

### R08 · P0 · 共用目标、两端分别实现：后台任务没有服从前台优先级

- **Android**：独立 `catalogWork` 已避免直接堵住前台执行队列，应保留；但它是连续跑完的大任务，`onPause/onStop` 未暂停该扫描，也未接入滚动、阅读、可见封面需求。DocumentsProvider 查询本身没有传入 CancellationSignal；代次检查须等 query 返回或遍历检查点，慢提供器取消仍可能滞后。
- **PC**：新扫描器每个 build 并行读取 8 个目录，却没有与普通目录的共享任务预算、封面及读取页的优先级协调；不同根目录或强制刷新仍可重叠。原目录服务的 24 个 stat 上限只限制 stat，并不限制新 scanner 的 readdir。
- **共用前端**：`useLibraryCatalog` 关闭时只丢弃 UI 回调，不自动停止原生任务；后台停止显示不等于后台停止 I/O。

**修复**：优先级统一为阅读/导航、可见封面、邻近有限预取、后台发现；按平台分批调度。后台任务允许在安全边界让出并续建。Android 尊重 Activity 生命周期、SAF 查询成本及取消能力；PC 按当前磁盘与前台工作负载限流。不要把 PC 8 路或 24 路直接照搬手机，也不要为了统一把 PC 全部串行化。

### R09 · P1 · PC 独有：轻量清单丢掉封面版本和时间排序所需信息

原 `directoryService.scanDirectory` 返回 size/modifiedAt。新 PC catalog 只取 Dirent 名称和类型，二者缺失；本轮实际模块诊断也确认其结果是 null。`LibraryPage:3652` 原封面复用依赖 `size:modifiedAt`，进入搜索/随机时变成 `":"`，与普通目录已加载封面的版本不相等，造成 UI 状态重置和重复请求。原生缩略图缓存仍可能接住请求，所以不是每次都重新解码。时间排序则把未知时间当 0，产生正确性问题。

**修复**：复用已有目录元数据；未知版本不能伪装成一个确定的新版本。按需补当前可见条目，持久摘要增量维护；封面身份与显示对象分离。修改时间排序必须具备相应数据，不能靠省略元数据伪造“排序很快”。也不能为修此问题把每次随机改成全库 stat。

Android `item(child)` 已包含 provider 给出的大小/时间，本项不是相同实现问题；无可靠修改时间的提供器另按版本/局部校验规则处理。

### R10 · P1 · PC 为主：每页 500 放大原有虚拟窗口和预取范围

`useContinuousLibrary:18` 普通 PC 分支的 windowRows 至少为 rowsPerPage，`LibraryPage:2480` 又把这个窗口全部作为封面目标，路径检查和页数统计也跟随它。此耦合在原版存在；本轮增加 500 后放大负担。四列、800px 视口、400px 行高且资源充足时，原版最大 200 档约 200 个槽位，现在 500 档约 500 个，而不是只挂载屏幕附近卡片。

**修复**：保留用户要求的 50/100/150/200/500，把逻辑页容量、实际 DOM 窗口、封面需求窗口分开。PC 仍保留适合桌面的预取量；Android 原本 exactPageSize 分支按视口限制窗口，不能为改 PC 把手机退回整页加载。平板新增列数只调整可见需求，不能顺带扩大成整库预取。

### R11 · P1 · 两端压缩包实现分别修：只要封面却准备所有内层包

嵌套压缩包兼容修复必须保留。普通有直接图片的 ZIP 已保留封面快捷路径，不能因为问题存在就一并回退。

- **PC**：`archiveService:174` 找不到直接图片时落到完整 `list`；后者串行展开所有内层包。`nestedArchiveCache:12/33` 的全局 extraction FIFO 限制内存是必要保护，但没有前台优先级，新阅读请求可能排在封面准备后面，绕过外层 archiveService 预留阅读通道的效果。新增 raw/flattened/ZIP 缓存还需联合记账，避免多套独立上限放大驻留。
- **Android**：`NativeArchives.cover:294` 无直接图片时调用 `images`，建立全部内层索引；非 ZIP 遇到内层包也立即落入此路径，可能错过后面本可直接使用的图片。`images/stage` 在对应实例锁内做较长工作。preview 与 reader 实例原本分离，不能为了去重合并它们的有状态解码器。

**修复**：封面专用按需下探，找到可用候选即可发布；失败候选按限额重试，不以所有子包准备完为条件。完整阅读页列表按阅读需要建立。PC 给内层准备队列加入优先级、去重、内存与磁盘预算；Android 有界分片、原生流式 staging，保留 reader/preview 隔离，可共享不可变元数据及经过验证的容器缓存。验证多内层包、坏子包、无直接图片以及封面并发中打开漫画。

### R12 · P1 · 共用对象规模问题，传输成本分端：全量复制和无关条目过多

当前流程同时持有原生全集、跨端结果、前端缓存、候选数组、去重 Map、匹配数组和父分支 Map；50 万条上限是条目上限，不是内存预算。路径越长，占用越大。

- **PC**：即使只要漫画，原生 build 仍保留每页图片，IPC handler 才过滤；根目录缓存也保存全条目。Electron 结构化传输产生额外对象，而不是 Android 的 JSON 字符串路径。
- **Android**：booksOnly 枚举时跳过图片记录，比 PC 少这部分，但搜索仍构造全部 JSONObject，转成一大段 JSON，再由 WebView `JSON.parse`；JSON 解析属于界面线程的额外突发工作。
- 两端对隐藏路径的排除都是 `items × hiddenPaths` 遍历，原版同类过滤用于单目录，本轮扩大至全库。扫描阶段还会进入被排除的分支。

**修复**：共用基础摘要和紧凑 ID，不存图片/封面内容；按批或按页传输所需字段，后续只送增量。隐藏分支在合法的目录边界尽早跳过，路径匹配结构按需求复用。分别统计 PC 主进程/渲染进程，以及 Android Java/WebView/原生位图内存，不能用“10 万个编号 0.4 MB”代替总占用。

### R13 · P1 · 共用：失效通知过宽，随机候选又没有相应更新

`LibraryPage:5087` 文件操作同步先 `invalidateLibraryCatalog()`，紧接着又按当前根目录调用，造成全局清空、代次递增和重复通知。旧扫描并不因此被立即停止，只是可能无法存回缓存。普通刷新也清掉当前根的整份索引。

`useRandomBrowse` 的独立 pool 则没有订阅索引失效；删除、改名后继续重抽可能复用旧路径。当前一边清太多，一边留了另一份旧副本。

**修复**：一次文件操作生成一次受影响路径/目录的更新，所有视图基于同一基础记录，合并通知。只让有关查询重新计算；删除的候选及时退出后续抽样。整库重建作为明确的维护动作。原版刷新已经有清缩略图逻辑，不能把所有清缓存都归为本轮新增，更不能借此删除用户主动刷新能力。

### R14 · P1 · 共用：随机专用准备链和筛选顺序不合理

收藏/书签开启随机，`LibraryPage:1054` 先以 4 个一批对全部记录 `checkResourcePath`，完毕才抽样。普通显示后还有自己的有限窗口路径检查。目录及收藏当前也是先抽 N 个，再应用搜索/标签，可能显示不足 N 项、假空或抽不到其他实际命中项。

**修复**：先得到当前范围与筛选条件的候选 ID，再沿共享排序路径生成随机顺序，只显示前 N 个。实际显示/打开时局部核验，失效项有限补位。阅读返回保留批次；调整页数量只改同一随机顺序的前缀。删除独立扫描/候选生命周期，清理无生产调用的 `collectRandomComics` 和遗留 background listDirectory 支路前先核对调用，不把死代码计为实际性能成本。

**应保护**：现有 `secureRandomIndex` 已使用 Web Crypto 和拒绝取样消除取模偏差，`sampleRandom` 是部分 Fisher–Yates。它不是造成数秒等待的证据点。本轮 10 万个短 ID 抽 50 项中位约 4.59 ms；目前 O(N) 去重分配可以移到基础清单维护，但不能改成有偏的随机比较排序，也不承诺完全消除计算成本。

### R15 · P0 验收补漏 · 共用，计数实现分端

原验证偏重最后结果和个别首屏，没有覆盖缓存命中、连续输入和后台竞争。`LocalLibrary` 的 directoryQueries 只在旧 children 中增加，新扫描的 resolver.query 没有进入该计数；旧的 2086 目录报告却只记录 2 次 directoryQueries，不能据此判断扫描几乎没有访问提供器。

**修复**：新增任务标识与来源计数，覆盖 scanner、普通目录、URI 解析、封面、页数、读取和写入；记录取消后仍运行的任务、排队/持锁时间、结果字节数及前端长任务。PC readdir/stat/解包/IPC 分开，Android provider query/SQLite 命中/桥接/位图内存分开。运行诊断默认轻量，不能每条资源写日志造成新的开销。

### R16 · P0 交互回归 · Android 为主，共用搜索会话也要修

手机键盘隐藏时关闭搜索，在原版 MobileLibraryBar 已存在；本轮进一步清空 query，并调用取消搜索，触发 R02 的缓存丢弃。因此“隐藏键盘与关闭搜索耦合”不能全部归为新增，但新版加重了后果。

**修复**：按最新需求，第一次 Back 只收输入法，第二次退出搜索，之后返回目录；关闭键盘事件不能清查询。搜索文件夹点击进入普通内容，返回恢复会话和滚动，不重新弹输入法。PC 单独保留 Esc 两阶段和前进按钮，不套用手机 Back。保护现有 mobileNavigation 的代次、首帧与生命周期处理，只改会话边界。

### 对照中没有归为新增性能错误的改动

- 原版手机已逐项解析查询、规范化文本，也已存在键盘隐藏关闭搜索的耦合；新增的是范围扩大及清查询/缓存等后果，分别按 R03/R16 修复。
- Android ZIP 索引从 zip2 切换为 zip3，其他原始归档索引使用 raw3，配合内层包元数据。升级首次重建这类派生索引有一次性成本，不等于持续重复重扫；先测第二次/重启后的复用，不能直接恢复旧键读取不完整的旧格式。
- 普通目录、可见封面队列和原生阅读器没有被整体替换。PC 新的直接封面与快速页数入口是在避免提前解包，应保留；其嵌套回退路径按 R11 单独修。
- 新增滚动位置记录有 160 个条目的上限，平板自适应仅按宽度调整列数；本轮没有证据证明它们本身是主要性能退化点。保护其功能，并在新列表规模下验证锚点与请求窗口。

## 3. 必须重点保护的优化

“保护”指保留行为和预算，不是永久禁止修改文件；任何必要调整均要先给出同场景对比。以下模块本轮已重新与原版核对，未改动的部分不能被顺手重写。

| 范围 | 原有能力与当前状态 | 新功能接入约束 |
| --- | --- | --- |
| 共用 | 连续虚拟列表、行高测量、窗口尺寸变化时的锚点；本轮增加有界滚动位置记录 | 保留返回位置；增量搜索按资源身份维护锚点，不用“把列表全部挂载”修跳动；修 R10 时保留原分页语义 |
| Android | `useMobileCoverQueue` 内容未变：并发 2、单张完成即发布、保留仍在需求窗口的请求，有限重试/缓存 | 禁止等待一批封面齐全再显示；索引不能把 wanted 换成全库，也不能不断改变版本造成请求取消重来 |
| Android | `thumbnailClient` 内容未变：相同路径任务共享、订阅计数、只取消无人需要的请求，分片间让出 | 新搜索/随机复用同一任务与版本；不能另开全量封面队列 |
| Android | LocalLibrary 原目录读取：短锁外执行 provider I/O、异步批量 SQLite 保存；URI 索引避免重启后逐层查询 | R05/R06 延伸这条路径；完整清单与有界热缓存职责分开，避免全库写入挤掉活动目录 |
| Android | 原文件夹封面：保存命中提示、一次约 60 ms/最多 8 步的可续建片段，附近请求优先 | 不因随机而取消断点、重复从根开始；后台索引与封面发现可复用事实但不能共用全局取消 |
| Android | `SeekableSource`、`NativeReaderSurface` 内容未变：pread 定位读取、原生显示、前台/预取分离、内存预算、保留上一完整帧、低内存回收 | 不把图片搬回 WebView，不让索引占阅读通道；不提高并发或扩大位图缓存来掩盖扫描慢 |
| Android | `mobileNavigation`、`SceneTransition`、`ResumeDrawGate` 内容未变：代次保护、真实绘制/恢复门控、生命周期取消 | 搜索会话和后台任务遵守既有导航生命周期，不能靠删除动画、缩短动画或超时强制放行隐藏卡顿 |
| PC | `directoryService` 内容未变：共享最多 24 个 stat 槽、取消移除等待者、自然排序、读取授权边界 | 新扫描纳入总 I/O 调度，但不能退成逐条串行；无须数据时不做全库 stat，需要时复用/按需补全 |
| PC | 原库封面调度仍以 6 个工作任务加载，逐项发布；缩略图服务缓存与重复任务合并仍在 | 保留桌面吞吐，修复版本一致性、视窗范围与前台竞争；不照搬手机并发 2 作为统一答案 |
| PC | archiveService 原全局限制、前台优先、预留 2 条前台通道、7z 并发最多 2 仍在 | 内层 staging 也必须遵守优先级，不允许新的串行子队列挡住原本保留的阅读通道 |
| PC | ZIP 目录索引、验证后的条目定位读取；缩略图直接图片快捷路径和新增快速页数查询 | 随机不解包；页数元数据不能为了“精确”提前展开全部内层包；普通档案继续按请求读页 |
| 共用但策略不同 | `preloadWindow`、图片处理/文档源模块未变：PC 原分辨率和字节预算；手机根据设备预算及阅读方向预取 | 保留画质与预算差异，新增索引不改变预加载设置、图像质量或读取模式 |

读取安全、现有授权、压缩包边界和 CRC 校验也随原读取路径保留；不以少做必要验证换取表面速度。嵌套包修复、长路径支持、平板自适应、返回滚动位置、书签页准确跳转均保留，性能问题在相应接入点修复。

## 4. 新功能应如何增量接入

### 4.1 共用规则

1. 原目录显示仍是首条路径。已有目录结果发布后，再把摘要投递给资源清单；不能先等全库再发布目录。
2. 搜索与随机只读取基础摘要，不直接驱动整库扫描/逐条路径预检查。清单按根目录和目录完成度持久化，后台独立补齐。
3. 单次扫描结果服务多个消费者；取消一个搜索只解除它的订阅。根目录切换、应用后台、读书和滚动按优先级调整后台工作。
4. 已知结果可先用，未完成范围明确标记；全库完成前不宣称全库均匀随机。新记录进入下一次重随机，不改变用户正在看的批次。
5. 文件夹名称匹配与文件匹配分别执行，文件夹在前、命中文件在后；输入立刻反馈，旧查询及时中止。
6. 实际显示按视口需要取得元数据、封面与路径状态；逻辑每页数量仅控制结果/页码，不能成为所有后台工作的请求数量。
7. 局部改变只更新相关摘要和查询，合并有限批量写入及界面更新；不重建根组件，不重发已完成的封面。

### 4.2 Android 接入

- 存储复用 SQLite 设施，增加独立的资源摘要/完成度/检查点，不把原 128 个目录快照或 32000 URI 热索引直接无限放大。
- 枚举考虑 SAF/provider 的慢查询、时间缺失和授权；尽可能传播取消，无法中止的当前查询不继续派发下一批。批次之间释放长锁。
- 已发现 URI 可复用且须保留授权验证；读取图片仍通过原生读取和显示，索引只传小批元数据。
- Activity 后台暂停主动发现，持久化检查点；前台恢复先显示，再空闲续建。
- 用低内存设备约束持续内存、Java 分配、WebView 长任务和电量相关后台工作量；模拟器数据不能代替实体设备结论。

### 4.3 PC 接入

- 保留 Electron 主进程文件服务，renderer 只接收可用摘要/结果，不把主进程 scanner 移到 renderer。大型排序/查询采用合适的分片或工作线程，不只给主线程外面套 async。
- 轻量 Dirent 发现继续可用；与已有 stat 元数据合并，按需完善版本/时间，不无条件恢复逐文件全库 stat。
- 按根/目录分块持久化并做原子局部更新，避免每次写一整个大 JSON；控制主进程与 renderer 两份数据的驻留及 IPC 载荷。
- 后台扫描、普通 stat、封面解码、7z、内层 staging 分别记账并协调前台预算；大库、机械盘、外置盘不能只按开发机 SSD 表现定并发。

## 5. 本轮诊断数据及其边界

环境：Windows x64、i5-12600KF、Node v24.7.0。函数各预热两次后测 7 次，以下为中位数。相同 1 万条短示例记录，无磁盘、UI、元数据查询及最终排序成本。

| 1 万条匹配 | 原版 PC | 原版手机函数在本机运行 | 当前共用函数 |
| --- | ---: | ---: | ---: |
| 空查询 | 0.19 ms | 45.34 ms | 44.51 ms |
| 普通单词 volume | 21.39 ms | 49.39 ms | 49.90 ms |

这说明：手机逐项函数在相同数据量下并未出现数量级变慢；新增的全库等待、缓存错误、输入时全库计算和其他后处理必须一起修。PC 的空查询快速路径确实被丢掉。上述数字不能换算为实体手机耗时，也不能从 44 ms 推断用户遇到的数秒卡顿只有一个原因。

随机函数从 1000/10000/100000 个短 ID 抽 50 个分别约 0.11/0.53/4.59 ms。该测试包括当前去重构建，但不包括加载候选、元数据、封面或界面绘制；支持把优先级放在准备链上。

已存在的上一轮端到端记录，本轮仅重读：PC 指定目录首张封面 2157 → 1164 ms，六张 2157 → 2168 ms。这个样本不支持“所有普通 PC 封面都更慢”，也无法排除本报告列出的搜索/随机切换、大库、500 档和嵌套包竞争问题。Android 2086 目录扫描 4274 ms 的旧报告只测了一个模拟器场景；其中旧 query 计数漏扫盘，见 R15。

## 6. 双端独立验收与修复顺序

**先做** R05、R02、R04、R13 等明确失效与快速路径修复，并补 R15 的观测。随后建立 R01/R06/R07/R08/R12 的渐进共享清单，再接入 R03/R14 的查询/随机，最后处理 R09/R10/R11 及 UI。不是先做完整随机功能，再补救基础加载。

| 验收维度 | PC | Android |
| --- | --- | --- |
| 同基线普通功能 | 同目录、配置和冷热条件测首屏、首张/首屏封面、开书、翻页、返回 | 同设备、WebView/provider、授权、缓存条件分别测；模拟器和实体分栏 |

| 搜索 | 首批与完整结果分开；逐字输入/删除、长路径、时间排序、跨视图版本复用 | 同样测输入；额外覆盖 IME/Back、慢 SAF、取消查询、键盘隐藏与读取返回 |
| 清单与重随机 | 已完成清单重随机不产生目录枚举、全量 stat 或解包；仅可见封面按需读取 | 重随机不产生全库 provider query；无结果时不死等，未知范围清楚标识 |
| 后台竞争 | readdir/stat/7z/staging 并发和前台等待分别记录 | provider、锁等待、SQLite 写入、应用暂停和恢复分别记录 |
| UI 与分页 | 50 到 500 的挂载数/封面请求按视窗预算增长，窗口缩放不丢位置 | 手机和平板/横屏分别测，按需窗口不扩大为整页或全库 |
| 资源与内存 | Electron 主进程、renderer、临时包磁盘占用、IPC 字节 | Java、WebView、原生位图、持久清单、临时包及查询计数 |
| 压缩包 | 普通 ZIP/RAR/7z 与嵌套包分开，封面负载中打开阅读 | 同格式另测 SAF，保留 ZIP pread、preview/reader 隔离及原生显示 |

测量至少覆盖多次冷/暖启动和连续操作，报告中位数、尾部等待和峰值；不能以一次最快结果通过。共同不变量必须直接断言：页面不等全库、取消不删有效清单、重随机不扫盘、后台不拦输入/导航、预算不随全库无界增长、旧请求不覆盖新界面。

原版没有全库搜索/随机，不能把原版“只查当前目录”与新版“查全库”的总完成时间直接作速度排名。普通已有功能与原版比较；新增能力分别验收首批、完整性、缓存复用和前台影响。两端分别通过，不能 PC 通过就宣布 Android 通过。
