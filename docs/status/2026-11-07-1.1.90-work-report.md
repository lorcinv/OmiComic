# OmiComic 1.1.90 工作报告

日期：2026-11-07。Android 1.1.90 / 10190；Windows 保持 1.1.88。本轮针对用户在一加 Ace 2、华为 MatePad 11 上反馈的普通阅读和全景放大拖动停顿、随后跳动，修复原生画面提交路径，并检查相关结构和内容安全边界。

**已修复并通过组件级新旧代码对照：画面的位置不再等待高清解码。** 已生成原签名 APK，作为本地修复验证包交付。本轮未完成 APK 的设备运行验证，不能据此宣称两台实体设备已无掉帧。

## 原因与 ComicScreen 对照

1.1.89 的 `NativeReaderSurface.commitFrame()` 在已有底图可显示时，仍用 `clearFrameReady()` 等待新的高清区域。输入和惯性位置继续前进，原生画面却保留旧位置，直到解码完成才追上。这与用户描述的“卡一下，然后图片闪过”一致。上版缩短了解码等待，却没有解除这个等待条件。

拖动越过当前高清区域时，还可能重新规划区域、取消仍然有用的进行中任务。PDF 的区域绘制越慢，位置被等待条件阻塞的时间就越长；这解释了它比压缩图片更明显的机制。本轮未重新测量实际 PDF 的解码耗时。

项目已有 ComicScreen 反编译源码 `H0/m.java` 中，拖动入口 `c()` 直接调用矩阵平移和 `y()`；惯性 `f.run()` 从 OverScroller 读取位移，更新矩阵并预约下一帧；`y()` 最终通过 `R()` 调用 `ImageView.setImageMatrix()`。这些位置更新路径没有等待文件读取或高清区域解码。因此，它不会受到 Omi 这一个提交条件的阻塞。

本轮调用 REA 的 Android 包检查接口时，因缺少 `REA_JADX_MCP_JAR` 返回不可用，随后读取项目已有 JADX 解包结果。完整来源背景见 [ComicScreen 对照记录](2026-11-07-comicscreen-panorama-analysis.md)。以上是静态调用路径对照，没有执行 ComicScreen 或测量两款软件的帧率，也没有复制第三方实现。

## 改动

应用逻辑只修改 `android/src/io/github/lorcinv/omicomic/NativeReaderSurface.java`：

- 底图具备完整可见覆盖后，立即提交最新几何位置；高清区域请求独立进行。旧高清像素按同一源图坐标随底图移动。
- 新露出的边缘允许暂时使用已有底图，解码完成后补清晰；不清空整幅画面，不让高清完成回调重新推动图片。
- 若较早的完成回调到达时已有更新的位置排队，先处理更新的位置，避免短暂回滚。
- 保留与当前视野相交、清晰度合适且符合预算的进行中区域，完成后再准备最新视野，减少反复取消。
- 取消或完成的高清任务仍通知下一次绘制；补图不再依赖“还有等待提交的底图帧”。
- 新区域未覆盖当前可见范围时，不替换正在显示的高清区域，避免局部任务完成造成清晰度反复切换。
- 待提交帧对工作线程可见，并使用一次读取的快照判断加载任务是否仍需要，避免判空后对象已被主线程清空的竞态。

保留普通翻页／首次显示的底图覆盖检查及原内存预算。没有调整拖动倍率、惯性参数、启动读取路径或 Windows 产品逻辑；`LocalLibrary.java`、`MainActivity.java`、`useReaderZoom.ts`、`useNativeReaderSurface.ts`、`ReaderPage.tsx` 与本轮开始时逐字节一致。

## 结构与安全边界检查

| 检查范围 | 结论与处理 |
| --- | --- |
| 输入、位置提交、高清解码之间的依赖 | 确认并解除“高清未就绪就冻结位置”的耦合，保留底图覆盖保护。 |
| 异步完成与最新输入的顺序 | 修复旧任务抢先提交及工作线程重复读取待提交帧的竞态。 |
| 任务取消、缓存与页面生命周期 | 保留有用的区域任务，补齐完成通知；继续使用原有代次校验、缓存预算和关闭流程，没有增加读取并发或预算。 |
| WebView 文件及网络访问 | Android 禁止直接 file/content 访问及混合内容；非应用域请求被阻止；消息端口发送给固定应用来源。 |
| 外部书籍内容 | EPUB 使用标签白名单，移除脚本、表单、嵌入页面和远程图片；对应清洗回归通过。 |
| Windows 主进程边界 | 保留上下文隔离、禁用页面 Node 集成、IPC 拒绝子框架调用及外部导航限制；只审查，未修改。 |

上述已检查边界中没有确认出可利用的安全漏洞。结构问题主要集中在同一个原生画面类同时管理位置提交、缓存和高清补图，之前的测试又把“持续全清晰”当作唯一合格条件，漏掉了“位置必须及时跟随”。本轮新增的延迟解码用例专门守住这个行为。阅读页与原生画面类的职责仍较多，后续拆分应逐步进行；本次没有做与故障无关的大规模重构。未进行全仓库依赖漏洞扫描或完整渗透审计。
