# 1.1.49 加载优化审查

后续用户复测仍发现全景拖动横向撕裂，先前检查未覆盖该现象。当前复查结论与本地测试见 [全景撕裂复查](2026-10-29-panorama-tearing-followup.md)。下列内容保留为当时的检查记录。

本次覆盖 Windows 与 Android 的打开入口、阅读初始化、图片就绪、预加载衔接，以及 PC 拖入提示与首次随机。

## 已确认并处理

| 问题 | 处理 | 范围 |
| --- | --- | --- |
| 清单读取后，入口和阅读器再次读取进度；阅读器还重复获取整份资源库资料 | 清单附带同次读取的设置与进度，入口和阅读器复用；兼容没有快照的旧调用 | 双端 |
| PC 首次打开与重新进入都会在图片准备好前显示阅读器 | 空闲时准备阅读模块，保留原界面直到实际单页／双页图片就绪，再显示同一个阅读器实例 | PC |
| 全景拖动同时由手势循环与界面重绘写入位移，小数位移改变采样位置 | 单独管理实时位移，提交布局时同步最新锚点；桌面位移对齐物理像素，图片页独立合成 | PC 像素与合成调整，共享位移同步 |
| 大库首批随机候选少，后续扫描无法补齐 | 保留已抽中前缀，接纳后续候选补足本批；达到数量后保持稳定 | 共享逻辑，PC 实测 |
| 拖入提示相对整窗定位，字号独立且带末尾句号 | 相对当前内容区居中，观察窗口尺寸变化，同步全局字号，去掉末尾句号 | PC |

Android 继续使用原生解码、现有预热和缓存。初始化快照单独克隆设置与当前进度，保持读写隔离，同时避免克隆整份资源库。PC 保留源文件版本核对、原图质量，以及现有解码和预读预算。

## Windows 对比样本

同机、同一份 20 页 CBZ，单页 2400 × 3400 像素，续读第 5、6 页双页。以双击事件至实际两张 DOM 图片可用计时；使用 DOM／图片事件，避免隐藏窗口动画帧节流影响统计。

| 场景 | 修改前图片可用 | 修改后图片可用 | 可见加载占位 |
| --- | --- | --- | --- |
| 首次打开 | 134.4 ms | 130.2 ms | 有 → 无 |
| 第一次重新进入 | 75.1 ms | 60.7 ms | 有 → 无 |
| 第二次重新进入 | 70.5 ms | 68.6 ms | 有 → 无 |

冷启动耗时没有明显下降，主要改善是减少重复读取与进入后的加载闪现。这组结果只覆盖当前样本，不外推为所有压缩格式和存储设备的提速比例。

PC 打开样本中的单独进度请求由每次 2 次降为 0 次。文件版本检查、取消打开、失败提示和超时处理继续保留。

## 随机与提示验收

- 120 个分组文件夹的真实冷扫描，首次得到的 11 个随机结果继续补到 50 个，无需重随机，已有前缀保持不变。
- 1440 × 960 窗口中，提示中心与右侧内容区中心均为 (830, 480)，调整窗口大小后仍保持居中。
- 全局字号从 14 改为 20，提示正文由 13 px 变为 18.5714 px，关闭按钮同步缩放，提示末尾没有句号。
- 读取进度与设置、打开取消、过期就绪回调、读写隔离均有针对性回归检查。Android 原生运行检查与发行附件校验随本次构建记录保存。

## 全景专项检查

- Windows 最大化和普通窗口尺寸、125% 显示缩放下的横向／纵向慢拖，四个物理像素对齐检查由失败变为通过。
- 延迟解码期间持续拖动、按住不动、惯性、横向／纵向／从右到左跳页、长图边界和缩放回归共 25 项通过。
- Windows 原生最大化、窗口恢复的横向与纵向拖动均有实际画面采样；每组检查位移前进、不倒退以及图像未变空白。另覆盖填满工作区高度的窄窗口，结果记录在 `output/loading-1149/panorama-native.json`。
- PC 的物理像素取整与图层调整限定为桌面布局，Android 保留原有原生绘制与位移精度。
- 审查中发现“进入阅读就绪”若复用于普通翻页，会等待尚未挂载的新页 DOM；已分离两种就绪条件，跳页和单双页切换回归通过。
