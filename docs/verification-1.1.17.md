## 持续模糊的修复

用户补充的异常图片为 PNG，3444×5120、约 9.5 MB，同书中还有同尺寸且更大的正常图片。该尺寸约 1763 万像素，未超过既有 1 亿像素上限；文件体积本身不能解释持续模糊。

源码确认了一个恢复缺口：大图先返回低清预览，随后补清晰；快速翻页取消补载后，预览可能仍在缓存中。再次显示该页时，界面有有效地址、原生层也有位图，原流程便把这一页当作已经就绪，没有重新补清晰。

现在每次提交可见页面都会检查清晰度，当前页重新接管被取消的补载；旧任务结束时也会复查，避免“新请求遇到旧任务尚未结束，双方都不再处理”的情况。正文清晰图使用前台队列，优先于相邻预读；真实失败最多尝试三次，取消不作为普通失败累加。最终失败会提示，避免无提示地停在模糊图，也不会无限重试。

验证采用同尺寸生成页面，通过独立测试工具构造“取消后缓存仍留下低清图”的可达状态，再让真实界面重新展示。旧版等待 5101 ms 后仍为低清；最终 APK 在 844 ms 内恢复到清晰图。另临时移除图片读取信息，制造两次真实读取失败，恢复信息后自动重试成功。该故障注入仅存在于独立测试 APK，发行包没有测试入口。

本轮没有拿到用户原图，不能据此断言这是原图唯一触发原因；报告区分了源码缺口、受控复现和原文件实测。

## PNG 处理与缓存

- 普通 PNG 保留已有逐行面积平均，避免线条和网点因直接抽样出现摩尔纹；没有为了速度切换到粗糙采样。
- 带色彩配置、交错编码等走 Android 原生分段过滤。原生源图工作缓冲按应用堆大小限制，最多 32 MiB，并串行处理，避免多个大缓冲并发。分块放大也按这一上限拆分，不再因单块原始像素过大直接放弃整个高清区域。
- 逐行解码遇到可恢复兼容问题时，在请求仍有效的前提下尝试 Android 备用解码；过期请求继续取消。
- 排队的清晰图补载只弱引用大 PNG 原始字节，避免快速跳页把多份十几 MB 的原页一直留在队列中。
- 已完成的 PNG 清晰底图由独立单线程保存，排队最多两项；翻页和退出不再直接取消有价值的底图保存。手动清理会使旧写入任务失效。

缓存默认策略：

| 内容 | 容量与退出行为 |
| --- | --- |
| 临时原始页面 | 默认 384 MiB；退出漫画后后台清理 |
| PNG 清晰底图及尺寸信息 | 默认最多 128 MiB；限额保留，旧内容自动淘汰 |
| 阅读磁盘缓存总预算 | 默认仍为 512 MiB；底图最多占用户总预算的一半且不超过 128 MiB |
| 原生正文、预览、图块缓存 | 退出阅读时清空引用；系统随后回收已不再使用的内存 |
| 流式来源的整包复制副本 | 退出后清理；原有单本 1 GiB、累计 1.5 GiB 边界不变 |
| 目录索引、封面相关资料、阅读记录 | 不属于退出漫画的清理范围 |

进程被直接结束时，下次启动后台清理残留临时原页和整包副本；文件读取等待这次清理完成，避免清理新会话刚写入的文件。快速退出又重开时，旧退出清理任务不能误清理新会话。

退出清理绑定到统一阅读状态，覆盖图片漫画、PDF 和 EPUB；文档阅读仍使用原来的画面通道。格式回归在实际打开 PDF／EPUB 后注入临时原页和整包副本，按返回退出后确认两类文件均被清理，阅读状态也已关闭。

这里的 512 MiB、128 MiB 是磁盘缓存限额，不是整个应用的 RAM 上限。正文内存仍采用原用户预算与设备上限；32 MiB 是受控的临时解码工作区，不是新增常驻缓存。缓存计数归零也不等于 Android 进程内存立即归零。

## 超大 PNG 打开与翻页

样本为 **1,916,865,148 字节，约 1.92 GB / 1.79 GiB，110 页，全部 3444×5120 PNG**。普通 Stored CBZ，使用真实 PNG 数据，没有无关填充。五种生成图像循环组成 110 页，包含普通 RGB、色彩配置和索引色透明 PNG，单页约 11.2–22.3 MB。生成入口：[mobile1117-fixtures.py](../tests/android/mobile1117-fixtures.py)。

计时检查原生位图的实际清晰度与尺寸，不把低清预览或有效图片地址算作正文完成。

| 测试条件 | 点击后清晰首屏 | 连续 8 次翻页确认清晰的中位数 | 本轮退出后立即重开 |
| --- | ---: | ---: | ---: |
| 1.1.16，冷阅读缓存（对照） | 1151 ms | 595.5 ms | 633 ms |
| 1.1.17，冷阅读缓存 | 1135 ms | 479 ms | 622 ms |
| 1.1.17，新进程，保留清晰底图 | 636 ms | 409 ms | 689 ms |
| 1.1.17，冷缓存，关闭正文预读 | 1124 ms | 566 ms | 618 ms |

首次打开仍须读取和解码原图，本轮没有证实首次打开在所有条件下稳定提速。主要改善是取消后的恢复、部分 PNG 编码路径，以及清晰底图缓存命中后的重复打开。立即重开的时间也包含界面进入和状态恢复，不能仅用这一个数值推断解码成本。

同一最终 APK、同一带色彩配置的 PNG，测试工具比较原先 8 MiB 分段方式与 32 MiB 分段方式：分别为 **693 ms / 350 ms**；实际解码入口为 **349 ms**。普通 PNG 继续使用实测更合适的逐行路径。[解码对比](../test-results/mobile1117-png-bench.json)

四轮超大 PNG 场景均通过：冷缓存、跨进程复开、关闭正文预读、连续 70 次翻页。每轮还检查六次远距离拖动、最后一页、可见预览恢复、退出清理及重开。清晰底图压力采样最高 **127.9 MiB**，未超过 128 MiB。

默认冷缓存轮退出前，临时原页占 **372.8 MiB**；退出后为 **0 字节**，清晰底图保留 **80.3 MiB**。70 次翻页压力轮退出后临时原页同样为 0，底图保留 **121.6 MiB**。各轮原生正文、预览、图块缓存计数在退出后归零；静止时没有持续解码循环。所有超大 PNG 轮次整包复制量均为 **0 字节**。
